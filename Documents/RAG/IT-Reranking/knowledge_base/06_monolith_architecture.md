# Монолитная архитектура

## Введение

Монолитная архитектура — это традиционный подход к разработке программного обеспечения, при котором всё приложение представляет собой единый развёртываемый артефакт. Все компоненты (UI, бизнес-логика, доступ к данным) находятся в одной кодовой базе и выполняются в одном процессе.

## Характеристики монолита

### Единая кодовая база
Весь код приложения находится в одном репозитории. Разработчики работают над общей кодовой базой, что упрощает понимание системы в целом.

### Единое развёртывание
Приложение собирается и развёртывается как один артефакт (JAR, WAR, бинарный файл). Любое изменение требует пересборки и передеплоя всего приложения.

### Общая база данных
Все модули приложения используют одну базу данных. Это упрощает транзакции и обеспечение целостности данных.

### Единый технологический стек
Всё приложение написано на одном языке и использует один фреймворк.

## Преимущества монолита

### Простота разработки
Один проект, одна IDE, одна конфигурация. Не нужно разбираться в распределённых системах, сетевых протоколах и межсервисной коммуникации.

### Простота отладки
Можно поставить breakpoint и пройти по всему коду от начала до конца. Stack trace показывает полную картину.

### Простота тестирования
End-to-end тесты просты — нужно запустить только одно приложение. Интеграционные тесты не требуют мокирования сетевых вызовов.

### Производительность
Вызовы между модулями — это обычные вызовы функций в памяти, а не сетевые запросы. Нет overhead на сериализацию и сетевую передачу.

### Согласованность данных
ACID-транзакции работают естественно, когда всё в одной базе данных. Не нужны сложные паттерны типа Saga.

### Низкие операционные затраты
Один сервер (или несколько за балансировщиком), один процесс мониторинга, простой деплой. Не нужен Kubernetes.

## Когда монолит — правильный выбор

### Небольшие команды (до 5-7 человек)
Для небольших команд микросервисы создают избыточную сложность. Монолит позволяет быстро двигаться без overhead на координацию между командами.

### Стартапы и новые проекты
В начале жизни продукта требования часто меняются. Монолит позволяет быстро экспериментировать и менять архитектуру без необходимости переделывать множество сервисов.

### Простые домены
Если бизнес-логика относительно проста и хорошо понятна, микросервисы привнесут только ненужную сложность.

### Ограниченные ресурсы
Микросервисы требуют развитой инфраструктуры: контейнеризация, оркестрация, мониторинг распределённой системы. Если нет ресурсов на это — монолит эффективнее.

### Прототипы и MVP
Когда нужно быстро проверить идею, монолит позволяет сосредоточиться на продукте, а не на инфраструктуре.

## Типы монолитной архитектуры

### Однослойный монолит
Простейший вариант — весь код в одном месте без явного разделения. Подходит только для очень маленьких проектов.

### Многослойный (Layered) монолит
Разделение на слои: Presentation, Business Logic, Data Access. Самый распространённый подход.

### Модульный монолит
Приложение разделено на модули с чёткими границами, но развёртывается как единое целое. Сочетает преимущества монолита и модульности микросервисов.

## Модульный монолит — золотая середина

Модульный монолит — это архитектурный стиль, который сохраняет простоту монолита, но привносит модульность микросервисов.

### Принципы:
- Чёткие границы между модулями
- Модули общаются через определённые интерфейсы
- Каждый модуль может иметь свою схему в БД
- Код организован по бизнес-доменам (как в микросервисах)

### Преимущества:
- Простота развёртывания монолита
- Чёткое разделение ответственности
- Возможность извлечь модуль в микросервис при необходимости
- Понятная кодовая база

### Пример структуры:
```
src/
├── modules/
│   ├── users/
│   │   ├── api/
│   │   ├── domain/
│   │   └── infrastructure/
│   ├── orders/
│   │   ├── api/
│   │   ├── domain/
│   │   └── infrastructure/
│   └── payments/
│       ├── api/
│       ├── domain/
│       └── infrastructure/
└── shared/
    └── kernel/
```

## Масштабирование монолита

### Вертикальное масштабирование
Добавление ресурсов серверу: больше CPU, RAM, быстрее диски. Простой подход, но имеет предел.

### Горизонтальное масштабирование
Запуск нескольких экземпляров приложения за балансировщиком нагрузки. Требует stateless-архитектуры.

### Кэширование
Redis или Memcached для кэширования данных. Значительно снижает нагрузку на базу данных.

### Оптимизация базы данных
Индексы, оптимизация запросов, read replicas, партиционирование таблиц.

## Проблемы монолита

### При росте команды
Когда команда вырастает до 10+ человек, координация становится сложной. Merge-конфликты, сложность code review, долгие сборки.

### При росте кодовой базы
Большой монолит сложно понять целиком. Время сборки и тестов растёт. Простые изменения требуют много времени.

### Связанность компонентов
В монолите легко создать неявные зависимости между модулями, что усложняет изменения.

### Технологические ограничения
Весь код должен использовать одну версию языка и библиотек. Обновление зависимостей затрагивает всё приложение.

## Эволюция от монолита

"Start with a monolith" — распространённый совет от экспертов. Начните с монолита, поймите домен, и только потом извлекайте микросервисы, когда в этом появится реальная необходимость.

### Признаки готовности к переходу:
- Команда > 10 человек
- Частые merge-конфликты
- Деплой стал рискованным мероприятием
- Разные части системы требуют разного масштабирования
- Чёткие границы доменов определились

## Заключение

Монолитная архитектура — это не устаревший подход, а разумный выбор для многих проектов. Модульный монолит сочетает простоту с хорошей организацией кода. Выбор между монолитом и микросервисами должен основываться на реальных потребностях команды и проекта, а не на хайпе.
