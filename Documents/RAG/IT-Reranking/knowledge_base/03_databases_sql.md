# Реляционные базы данных (SQL)

## Введение в реляционные СУБД

Реляционные базы данных хранят данные в виде таблиц со строками и столбцами. Они используют SQL (Structured Query Language) для управления данными и обеспечивают строгую согласованность через ACID-транзакции.

## Популярные реляционные СУБД

### PostgreSQL

PostgreSQL — это мощная объектно-реляционная система управления базами данных с открытым исходным кодом. Она известна своей надёжностью, богатым набором функций и соответствием стандартам.

**Ключевые особенности:**
- Полная поддержка ACID
- Расширенные типы данных (JSON, массивы, геометрия)
- Мощная система индексов (B-tree, Hash, GiST, GIN)
- Поддержка полнотекстового поиска
- Материализованные представления
- Триггеры и хранимые процедуры
- Расширения (PostGIS, pg_trgm, pgvector)

**Производительность PostgreSQL:**
PostgreSQL отлично справляется со сложными запросами и большими объёмами данных. Поддерживает параллельное выполнение запросов, эффективное использование памяти и продвинутую оптимизацию запросов.

**Когда использовать:**
- Сложные приложения с комплексными запросами
- Геопространственные данные (с PostGIS)
- Полнотекстовый поиск
- Когда нужна максимальная надёжность

### MySQL

MySQL — одна из самых популярных СУБД в мире, особенно для веб-приложений. Принадлежит Oracle Corporation.

**Ключевые особенности:**
- Высокая скорость для простых запросов
- Различные движки хранения (InnoDB, MyISAM)
- Репликация master-slave
- Широкая поддержка хостингов
- Простота использования

**Ограничения MySQL:**
- Менее развитая поддержка сложных запросов
- Ограниченная поддержка стандартов SQL
- Некоторые функции только в платной версии

**Когда использовать:**
- Веб-приложения с простыми запросами
- LAMP-стек
- Когда нужна широкая совместимость

### SQLite

SQLite — это встраиваемая СУБД, которая хранит всю базу данных в одном файле. Не требует отдельного сервера.

**Ключевые особенности:**
- Нулевая конфигурация
- Один файл базы данных
- Кроссплатформенность
- ACID-совместимость
- Идеален для мобильных приложений

**Когда использовать:**
- Мобильные приложения
- Embedded-системы
- Локальное хранение данных
- Прототипирование

## Миграция между базами данных

### Миграция с MySQL на PostgreSQL

Переход с MySQL на PostgreSQL — распространённая задача, которая требует внимательного планирования.

**Основные различия в синтаксисе:**

| MySQL | PostgreSQL |
|-------|------------|
| AUTO_INCREMENT | SERIAL или IDENTITY |
| TINYINT(1) для boolean | BOOLEAN |
| ENUM как тип | ENUM через CREATE TYPE |
| LIMIT offset, count | LIMIT count OFFSET offset |
| \`backticks\` для идентификаторов | "двойные кавычки" |

**Проблемы при миграции:**
1. **Типы данных**: Различия в типах требуют маппинга
2. **Функции даты/времени**: NOW() vs CURRENT_TIMESTAMP
3. **Строковые функции**: CONCAT vs || оператор
4. **Case sensitivity**: PostgreSQL чувствителен к регистру в идентификаторах
5. **Хранимые процедуры**: Полностью разный синтаксис

**Инструменты миграции:**
- pgLoader — автоматическая миграция
- AWS DMS — для облачных миграций
- Ручной экспорт/импорт через CSV

**Рекомендации:**
1. Создайте полную схему в PostgreSQL
2. Проверьте совместимость типов данных
3. Мигрируйте данные порциями
4. Тщательно протестируйте приложение
5. Обновите SQL-запросы в коде

## ACID-транзакции

ACID — это набор свойств, гарантирующих надёжность транзакций:

- **Atomicity (Атомарность)**: Транзакция выполняется полностью или не выполняется вообще
- **Consistency (Согласованность)**: База данных переходит из одного согласованного состояния в другое
- **Isolation (Изолированность)**: Параллельные транзакции не влияют друг на друга
- **Durability (Долговечность)**: Завершённые транзакции сохраняются даже при сбое

## Индексирование

Индексы критически важны для производительности запросов.

### Типы индексов:

**B-tree (по умолчанию):**
- Подходит для операций сравнения (<, >, =, BETWEEN)
- Эффективен для сортировки
- Самый универсальный тип

**Hash:**
- Только для операций равенства (=)
- Быстрее B-tree для точных совпадений
- Не поддерживает диапазоны

**GIN (Generalized Inverted Index):**
- Для составных значений (массивы, JSON, полнотекстовый поиск)
- Эффективен для поиска элементов в коллекциях

**GiST (Generalized Search Tree):**
- Для геометрических данных
- Поддержка нечёткого поиска

### Стратегии индексирования:

1. Индексируйте столбцы в WHERE и JOIN
2. Используйте составные индексы для частых комбинаций
3. Избегайте избыточных индексов
4. Регулярно анализируйте использование индексов

## Оптимизация запросов

### EXPLAIN ANALYZE
Используйте EXPLAIN ANALYZE для понимания плана выполнения запроса.

### Основные оптимизации:
1. Используйте подходящие индексы
2. Избегайте SELECT *
3. Ограничивайте результаты (LIMIT)
4. Используйте соединения вместо подзапросов
5. Денормализуйте данные при необходимости

## Репликация и масштабирование

### Репликация
- **Master-Slave**: Один мастер, несколько реплик для чтения
- **Master-Master**: Запись на несколько серверов (сложнее в управлении)

### Шардинг
Горизонтальное разделение данных по нескольким серверам. Требует тщательного планирования ключа шардинга.

## Заключение

Реляционные базы данных остаются фундаментом для большинства приложений благодаря своей надёжности, согласованности и мощному языку запросов SQL. Выбор между PostgreSQL, MySQL и другими СУБД зависит от конкретных требований проекта.
