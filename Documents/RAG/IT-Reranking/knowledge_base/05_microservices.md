# Микросервисная архитектура

## Введение

Микросервисная архитектура — это подход к разработке программного обеспечения, при котором приложение строится как набор небольших, независимых сервисов. Каждый сервис выполняет одну бизнес-функцию и может быть развёрнут независимо.

## Основные принципы

### Единая ответственность
Каждый микросервис отвечает за одну конкретную бизнес-функцию. Например: сервис авторизации, сервис заказов, сервис уведомлений.

### Независимое развёртывание
Сервисы можно обновлять, масштабировать и развёртывать независимо друг от друга без остановки всего приложения.

### Децентрализация
- Децентрализованное управление данными (каждый сервис имеет свою БД)
- Децентрализованное управление (каждая команда владеет своими сервисами)
- Технологическая свобода (разные сервисы могут использовать разные технологии)

### Отказоустойчивость
Сбой одного сервиса не должен приводить к падению всей системы. Используются паттерны: Circuit Breaker, Bulkhead, Retry.

## Преимущества микросервисов

### Масштабируемость
Можно масштабировать только те сервисы, которые испытывают нагрузку, а не всё приложение целиком. Это экономит ресурсы и позволяет оптимально использовать инфраструктуру.

### Гибкость разработки
Разные команды могут работать над разными сервисами параллельно, не мешая друг другу. Ускоряется time-to-market для новых функций.

### Технологическая независимость
Каждый сервис может быть написан на наиболее подходящем языке и использовать оптимальную базу данных для своих задач.

### Устойчивость к отказам
Изоляция сервисов означает, что сбой в одном компоненте не приведёт к каскадному отказу всей системы.

### Простота понимания
Небольшие сервисы легче понять, поддерживать и тестировать, чем огромный монолит.

## Когда микросервисы имеют смысл

### Подходящие сценарии:

**Крупные команды (10+ разработчиков):**
Микросервисы позволяют разделить команду на независимые группы, каждая из которых владеет своими сервисами. Это уменьшает координацию и ускоряет разработку.

**Высоконагруженные системы:**
Когда разные части приложения имеют разные требования к производительности, микросервисы позволяют масштабировать только нужные компоненты.

**Частые релизы:**
Если требуется выпускать обновления несколько раз в день, независимые деплои микросервисов значительно упрощают процесс.

**Разнородные требования:**
Когда разные части системы требуют разных технологий (например, ML-сервис на Python, API на Go, обработка данных на Scala).

### Метрики готовности:
- Команда > 10 человек
- Понятные границы доменов
- Зрелые DevOps-практики
- Опыт работы с распределёнными системами

## Коммуникация между сервисами

### Синхронная коммуникация

**REST API:**
Самый распространённый способ. Сервисы общаются через HTTP-запросы. Простой и понятный, но создаёт связанность.

**gRPC:**
Бинарный протокол от Google. Быстрее REST, строгая типизация через Protocol Buffers. Хорош для внутренней коммуникации.

### Асинхронная коммуникация

**Message Queues (RabbitMQ, AWS SQS):**
Сервис отправляет сообщение в очередь, получатель обрабатывает когда готов. Обеспечивает слабую связанность.

**Event Streaming (Apache Kafka):**
События публикуются в топики, подписчики получают их в реальном времени. Идеален для event-driven архитектуры.

## Паттерны микросервисов

### API Gateway
Единая точка входа для всех клиентов. Занимается маршрутизацией, аутентификацией, rate limiting.

### Service Discovery
Сервисы регистрируются в реестре (Consul, Eureka), клиенты находят их динамически.

### Circuit Breaker
Защита от каскадных отказов. При множественных ошибках сервиса запросы прекращаются на время.

### Saga
Управление распределёнными транзакциями через последовательность локальных транзакций с компенсациями.

### CQRS
Разделение команд (изменение данных) и запросов (чтение данных) в разные модели.

## Инфраструктура

### Контейнеризация
Docker — стандарт для упаковки микросервисов. Обеспечивает консистентность между средами.

### Оркестрация
Kubernetes управляет контейнерами: деплой, масштабирование, самовосстановление.

### Service Mesh
Istio, Linkerd — управление трафиком, безопасность, наблюдаемость на уровне инфраструктуры.

## Наблюдаемость

### Логирование
Централизованный сбор логов (ELK Stack, Loki). Корреляция логов через trace ID.

### Метрики
Prometheus + Grafana для сбора и визуализации метрик.

### Трейсинг
Jaeger, Zipkin для отслеживания запросов через множество сервисов.

## Типичные ошибки

1. **Слишком мелкое дробление**: Создание отдельного сервиса для каждой функции приводит к хаосу
2. **Игнорирование сетевых проблем**: Сеть ненадёжна, нужна обработка таймаутов и ретраев
3. **Синхронная зависимость**: Цепочки синхронных вызовов снижают надёжность
4. **Общая база данных**: Нарушает независимость сервисов
5. **Отсутствие мониторинга**: Распределённую систему невозможно отлаживать без наблюдаемости

## Заключение

Микросервисы — мощный инструмент для масштабирования разработки и систем. Однако они привносят значительную сложность и требуют зрелой инфраструктуры и команды. Для большинства проектов разумно начать с монолита и переходить к микросервисам по мере роста.
