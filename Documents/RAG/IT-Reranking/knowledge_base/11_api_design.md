# Проектирование API

## Введение

API (Application Programming Interface) — это контракт между сервисами, определяющий как они взаимодействуют. Хорошо спроектированный API интуитивно понятен, консистентен и легко поддерживается.

## REST API

REST (Representational State Transfer) — архитектурный стиль для создания веб-сервисов, основанный на HTTP-протоколе.

### Принципы REST

**Stateless (Без состояния):**
Каждый запрос содержит всю информацию, необходимую для его обработки. Сервер не хранит состояние клиента между запросами.

**Uniform Interface:**
Единообразный интерфейс через стандартные HTTP-методы и URL-структуру.

**Resource-based:**
API оперирует ресурсами (существительными), а не действиями (глаголами).

### HTTP-методы

| Метод | Действие | Идемпотентность |
|-------|----------|-----------------|
| GET | Получить ресурс | Да |
| POST | Создать ресурс | Нет |
| PUT | Заменить ресурс | Да |
| PATCH | Частично обновить | Нет |
| DELETE | Удалить ресурс | Да |

### Дизайн URL

**Хорошие практики:**
```
GET    /users              # Список пользователей
GET    /users/123          # Конкретный пользователь
POST   /users              # Создать пользователя
PUT    /users/123          # Обновить пользователя
DELETE /users/123          # Удалить пользователя

GET    /users/123/orders   # Заказы пользователя
GET    /users/123/orders/456  # Конкретный заказ
```

**Плохие практики:**
```
GET    /getUser?id=123     # Глагол в URL
POST   /createUser         # Глагол в URL
GET    /user/123           # Единственное число
```

### HTTP-статусы

**2xx — Успех:**
- 200 OK — успешный запрос
- 201 Created — ресурс создан
- 204 No Content — успех без тела ответа

**4xx — Ошибка клиента:**
- 400 Bad Request — невалидный запрос
- 401 Unauthorized — требуется аутентификация
- 403 Forbidden — нет прав доступа
- 404 Not Found — ресурс не найден
- 422 Unprocessable Entity — ошибка валидации

**5xx — Ошибка сервера:**
- 500 Internal Server Error — внутренняя ошибка
- 503 Service Unavailable — сервис недоступен

### Версионирование

**В URL:**
```
/api/v1/users
/api/v2/users
```

**В заголовке:**
```
Accept: application/vnd.api+json; version=1
```

**Рекомендации:**
- Начинайте с v1
- Поддерживайте старые версии
- Документируйте изменения
- Используйте семантическое версионирование

### Пагинация

**Offset-based:**
```
GET /users?offset=20&limit=10
```

**Cursor-based (рекомендуется):**
```
GET /users?cursor=abc123&limit=10
```

**Формат ответа:**
```json
{
  "data": [...],
  "pagination": {
    "total": 100,
    "limit": 10,
    "next_cursor": "xyz789"
  }
}
```

### Фильтрация и сортировка

```
GET /users?status=active&role=admin
GET /users?sort=created_at&order=desc
GET /users?fields=id,name,email
```

## GraphQL

GraphQL — это язык запросов для API, разработанный Facebook. Клиент запрашивает только нужные данные.

### Основные концепции

**Schema:**
Описание типов данных и операций.

```graphql
type User {
  id: ID!
  name: String!
  email: String!
  orders: [Order!]!
}

type Query {
  user(id: ID!): User
  users: [User!]!
}

type Mutation {
  createUser(name: String!, email: String!): User!
}
```

**Query:**
```graphql
query {
  user(id: "123") {
    name
    email
    orders {
      id
      total
    }
  }
}
```

### Преимущества GraphQL:
- Клиент получает только нужные данные
- Один endpoint вместо множества
- Строгая типизация
- Самодокументируемый (introspection)

### Недостатки GraphQL:
- Сложность кэширования
- N+1 проблема
- Сложнее отслеживать производительность
- Выше порог входа

### Когда использовать:
- Мобильные приложения (экономия трафика)
- Сложные связи между данными
- Множество клиентов с разными потребностями

## gRPC

gRPC — высокопроизводительный RPC-фреймворк от Google, использующий Protocol Buffers.

### Особенности gRPC

**Protocol Buffers:**
Бинарный формат сериализации, более эффективный чем JSON.

```protobuf
syntax = "proto3";

service UserService {
  rpc GetUser(GetUserRequest) returns (User);
  rpc ListUsers(ListUsersRequest) returns (stream User);
}

message User {
  string id = 1;
  string name = 2;
  string email = 3;
}
```

**Типы RPC:**
- Unary — один запрос, один ответ
- Server streaming — один запрос, поток ответов
- Client streaming — поток запросов, один ответ
- Bidirectional — двусторонний поток

### Преимущества gRPC:
- Высокая производительность
- Строгие контракты
- Генерация кода для клиентов
- Поддержка стриминга

### Недостатки:
- Не работает в браузере напрямую
- Сложнее отлаживать (бинарный формат)
- Меньше инструментов

### Когда использовать:
- Микросервисы (внутренняя коммуникация)
- Высокая нагрузка
- Real-time приложения

## WebSocket

WebSocket — протокол для двустороннего общения в реальном времени.

### Использование:
- Чаты и мессенджеры
- Real-time уведомления
- Онлайн-игры
- Collaborative editing

### Альтернативы:
- **Server-Sent Events (SSE)**: Односторонний поток от сервера
- **Long Polling**: HTTP-запросы с ожиданием
- **WebTransport**: Новый протокол на базе HTTP/3

## Безопасность API

### Аутентификация

**API Keys:**
Простой способ, подходит для server-to-server.

**JWT (JSON Web Tokens):**
Stateless токены с подписью.

**OAuth 2.0:**
Стандарт для делегированного доступа.

### Защита

- **HTTPS**: Обязательно
- **Rate Limiting**: Ограничение частоты запросов
- **Input Validation**: Проверка входных данных
- **CORS**: Контроль кросс-доменных запросов

## Документация

**OpenAPI (Swagger):**
Стандарт описания REST API. Автогенерация документации и клиентов.

**Инструменты:**
- Swagger UI — интерактивная документация
- Postman — тестирование и документация
- Redoc — красивая документация

## Заключение

Выбор типа API зависит от требований проекта. REST подходит для большинства случаев, GraphQL — для сложных клиентских приложений, gRPC — для высокопроизводительных внутренних коммуникаций.
